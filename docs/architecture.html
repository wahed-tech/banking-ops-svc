Banking Ops Portal: Architecture

Actions (changes money / state) Viewing data (read-only) Thredd files Griffin webhooks

How it works

Viewing data

  1. Ops user signs in with Google (SAML SSO via Supabase).
  2. The portal reads from the Supabase database directly.
  3. Database rules make it read-only for the portal. Audit log, limits and bank details are hidden.

Example: a new metric is just a Supabase view plus a chart. No backend change.

Actions (e.g. a transfer)

  1. Ali clicks Create. The portal calls banking-ops-svc directly with his login token.
  2. banking-ops-svc saves the transfer as PENDING and logs "Ali CREATED".
  3. Sara approves. The service checks Sara ≠ Ali, then logs "Sara APPROVED".
  4. banking-ops-svc calls Griffin and logs SENT or FAILED.

Thredd files

  1. Thredd pushes files to our existing SFTP, which lands them in S3.
  2. banking-ops-svc matches recon / settlement data.
  3. It writes the results to Supabase, and ops read them there.

Rules

  • Shows data only → read Supabase directly.
  • Changes anything → goes through banking-ops-svc.
  • banking-ops-svc checks the login token on every call, and only the portal's website can call it.
  • The portal holds no secrets. The Griffin token stays in AWS.
  • Audit log is append-only: a new row for every step, never edited.
  • The user's token is forwarded, so every action logs the real person.
  • Griffin is called only from banking-ops-svc. Griffin accepts only our AWS IP.
